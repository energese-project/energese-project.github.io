The language

Howard T. Odum’s Energy Systems Language is a graphical language for modelling flows of energy, matter, money and information through complex systems (Odum & Odum, 2000). Its discipline is a rule about what a drawing may say:

Edges are flows only — pathways carrying energy, matter, money, information or code from one unit to another. Nodes are everything else — processing units, storages, sources, sinks, gates, amplifiers, converters and transaction points. Even when a node has no dynamics beyond a fixed coefficient k, that coefficient is the state of the node: it is a property of the unit, not of the flow passing through it.

Odum’s fundamental symbols are implemented as node primitives, each with defined semantics rather than a picture:

Odum symbol Name Type

An unrecognised type string is rejected at load time, naming the node and the offending string, so a typo fails loudly instead of quietly becoming a storage node.

How it is built

One C99 core, deployed to native, WebAssembly, Swift, Python and JavaScript. The kernel is deliberately not a general-purpose ODE library — no stiff-solver zoo, no symbolic Jacobian engine, no automatic differentiation framework, no GUI builder. The schema is the interface contract, and visualisation is a downstream concern.

Everything is MIT licensed and developed in the open at github.com/energese-project. Issues and pull requests are welcome on each repository; the contribution standards live in the AGENTS.md at each repository root.

Precedent

This is a second attempt at a programme someone else wrote down first. In 2004 Raphaël Valyi and Enrique Ortega described EmSim, an open-source Java implementation of the Energy Systems Language that drew diagrams, translated them into differential equations, integrated them, and propagated emergy across the resulting network. The six motivations they gave for building it transfer almost unaltered: models are not shareable without a standard, a diagram is not a specification until the translation to equations is fixed, transformity values are being lifted from published tables into systems where they do not belong, and none of it is fixable inside commercial software.

That the same list can be written twice, twenty-two years apart, is worth stating plainly rather than presenting the motivations as new. One item has been added to it. EmSim solved sharing a model and never asked about re-executing one — determinism, seeding and version pinning appear nowhere in the paper — and its own history shows the difference: the files are still downloadable, and the runtime that reads them is what decayed. An emergy figure derived from a simulated trajectory is the output of an execution, not a document, and a figure that cannot be regenerated cannot be audited.

EmSim is also ahead of this kernel in one place. It implemented Odum’s prohibition on re-adding co-products, taking a maximum over pathways descending from a common co-production — the rule GSSK is missing. It got that rule cheaply because it enumerated pathways, which is the same choice that made it scale badly, and the trade between the two designs is the most useful thing the paper has to say to this one.
